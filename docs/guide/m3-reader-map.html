YomiKoe M3: the reader that keeps the page in step with the voice

Milestone 3 builds the browser side: one HTTP fetch per sentence, Web Audio buffers scheduled back to back, and a highlight that asks the audio clock where it is on every frame. This page is the live status of that work, one diagram per mechanism, and the phase ledger with evidence.

1What the milestone must prove

PLAY-1 to PLAY-5: play, pause, skip by sentence and by section; the current word and sentence highlighted in sync; click any sentence to seek; a voice or speed change mid-play that resumes at the current sentence and flushes the lookahead; gapless stitching with no click at boundaries. The pickers for voice and speed ship with it. The library view, remembered positions, keyboard shortcuts and lock-screen controls are M4.

Gate (Technical Design, testing row "Playback (browser)") Playwright loads a 30-segment document served by the API with the FakeBackend, plays for 20 s, and at three probe times the highlighted word is the expected word. A click on a sentence seeks there. A speed change mid-play restarts the sentence at the new speed. Asserted on Chromium; WebKit and Firefox reported.
Why the FakeBackend makes the gate exact

It emits 80 ms of silence per word, words back to back, timestamps evenly spaced. The expected word at any second of playback is arithmetic, so the test can assert sync to within one word without listening.

Why no Node toolchain was a phase of its own

The machine has no Node, no npm and no Homebrew. Phase 0 installs Node LTS user-locally from the official tarball with its checksum verified, then scaffolds web/. Nothing in M3 runs until that is green.

2The delivery loop (D5)

The browser asks for one sentence at a time. The API answers with encoded audio and the word timestamps in a header. The player decodes it, schedules it to start exactly when the previous buffer ends, and keeps two sentences fetched ahead while the server keeps five synthesized ahead. A seek or a settings change stops every scheduled source, bumps a generation counter so late arrivals are ignored, and starts a fresh schedule from the target.

Why not a stream

Media Source Extensions want one continuous stream; per-sentence Opus files would mean append windows and timestamp offsets, and iOS Safari only supports MSE as ManagedMediaSource. Sentence-sized GETs need none of that (D5).

Why pause is suspend()

Buffer sources cannot pause. Suspending the context freezes the hardware clock and every scheduled source together, so resume is sample-exact and the schedule is never rebuilt for a pause (D24, proposed).

3The player state machine (D10)

Five states, one pure reducer, side effects in one hook. Components dispatch events and never touch the audio API. Seek and settings changes pass through loading so the schedule is rebuilt exactly once; a generation number carried in the context makes every audio event self-identifying, so a response for a schedule that no longer exists cannot move the machine.

4Clock to word (D8)

The highlight never runs on a timer. Each animation frame reads AudioContext.currentTime, finds the scheduled entry whose window contains it, subtracts that entry's start time to get the elapsed milliseconds into the sentence, and binary-searches the sentence's timestamps for the active word. Two class toggles follow; React is not involved on that path.

5Tokens and timestamps

The reader renders every sentence before any audio exists, so it cannot build word spans from timestamps. It splits the text on whitespace into tokens with character offsets. When a clip arrives, each timestamp (whose offsets already point into the same text, translated by the API through the normalizer's char map) is assigned to the first token whose span overlaps it. The highlight unit is the token; the mapping is computed once per sentence.

The mitochondria (Fig. 2) divide. Spores form in the cortex.

How the highlight will read: sentence tint, word tint, both chosen for 4.5:1 contrast in light and dark themes.

Cause: the normalizer empties such segments, the server answers a header-only WAV (0 ms, no timestamps), the browser's decoder rejects it, and the reader took that as a fetch failure of a prefetched sentence. Fix (2ad5121, merged aeb116d): an empty clip is a zero-length entry and the next sentence chains at the same instant; a failed prefetch of a non-current sentence is skipped with a warning, only a failure on the current sentence reaches error. 66 unit cases, gate 9 of 9, live run from order 220 through the marker to 223 while playing (460–463). The parser should drop these markers as page numbers; that is ING-4 work in M4 (230 of them in this book).

Things to know now

  • No Node, npm or Homebrew on this machine at the start of M3; Node now lives under ~/.local/node and Playwright's browsers under ~/.local/ms-playwright; nothing else outside the repo was touched. Every command in web/ starts with source web/scripts/env.sh.
  • The API has no position endpoint yet; the reader keeps position in memory until M4 (LIB-2).
  • The M2 guide stays the reference for synthesis and the audio protocol: YomiKoe M2 Synthesis Map; M1 for ingestion: YomiKoe M1 Ingest Map.
