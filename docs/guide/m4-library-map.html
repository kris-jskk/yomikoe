HearNarro M4: a library that remembers where you were

Milestone 4 turns the reader into something you return to: a library of documents with progress, a position saved every few seconds, voice and speed remembered per document, delete, keyboard and lock-screen controls, skip toggles for footnotes, captions and references, the remaining ingestion rules (tables, equations, OCR, sections), and one container that serves it all. This page is the live status: one diagram per mechanism, and the phase ledger with evidence.

3Library list and progress (LIB-1)

GET /documents grows from a list of names into the library's data: segment count, saved position, progress, settings and last opened. Progress is not stored; it is derived on every request from the saved position, so it can never disagree with where the reader will resume.

Why it is needed

Without a library the user has to remember which document they were in and re-upload it. LIB-1 makes the home page a list of everything already ingested.

Why no migration

The documents table already has position, voice, speed and last_opened_at columns from M1; LIB-1..4 add routes, not columns (OCR's ocr_skipped_pages is the only new column, migration 0004).

4Position save and restore (LIB-2, D26 proposed)

While playing, the hook sends PATCH /documents/{id} with the current segment and the audio time into it every 5 s and on every PAUSE. When the tab is closed, pagehide sends the last known value with fetch(..., {keepalive: true}). On the next open, the reader scrolls to that segment and the first Play starts there at the saved offset.

Why it is needed

LIB-2 requires the position saved every 5 s and on pause; M3 kept it in memory only, so a reload started from the top.

Why keepalive fetch, not sendBeacon (D26, proposed)

sendBeacon can only POST and cannot send a JSON content type without a Blob workaround. A keepalive fetch sends the same PATCH as everything else: one endpoint, one code path.

5Settings precedence (LIB-3)

Voice and speed come from the document if it has its own, otherwise from the global default (GET /settings, speed 1.25 when unset). A change in the reader writes to that document only, debounced 500 ms; the library's default controls never touch a document that already has settings.

Why it is needed

LIB-3: each document keeps the voice and speed it was last heard in, and a new document starts from a default the user chose once.

Why changes during loading are queued

M3 deviation 6 dropped a settings change made while a sentence was loading; M4 applies it when the load finishes.

6Delete cascade (LIB-4)

DELETE /documents/{id} removes the database rows (cascading to blocks, segments, sections and audio cache rows), the stored PDF and the document's audio directory, then returns 204. It refuses with 409 while the document is still parsing, so it never races the ingest worker.

Why it is needed

LIB-4: cached audio is the largest thing on disk (every voice and speed a document was heard at); deleting a document must free it.

Why 409 while parsing

The ingest worker is still writing rows; deleting under it would leave orphans or a crash. The user waits for ready or failed.

7Keyboard and Media Session (PLAY-6, PLAY-7)

One keydown listener on document and the navigator.mediaSession handlers are both thin maps onto the dispatches the PlayerBar buttons already use. Neither has logic of its own; the machine stays the only place playback state changes (D10).

Why it is needed

PLAY-6 asks for space, arrows and +/-; PLAY-7 for lock-screen controls on phone browsers. Lock-screen behaviour on a real phone stays a manual check.

Why pure maps

A pure key map and handler wrapper are unit-testable without a browser (keys.test.ts), and keeping state in the one reducer file is D10.

8Skip toggles (PLAY-8)

Three toggles in the PlayerBar: footnotes, captions and references. Footnotes and captions are picked by block type. References is a span: from a heading whose text matches the references pattern up to the next heading. Skipped segments are dimmed, never scheduled, and jumped over by skip and seek.

Why it is needed

PLAY-8: footnotes, captions and a long references list interrupt listening; the user wants to mute them without re-ingesting.

Why localStorage here

Skip choices are a per-viewer convenience, not document data; losing them in a private window is harmless, so they stay off the server.

9Sections written at ingestion (ING-8, closes D25)

Ingestion writes a sections row for every heading block, pointing at the first segment of that block, and stamps every following segment with that section_id. Documents ingested before this change keep empty sections and the client keeps deriving them from headings (D25).

Why it is needed

ING-8: a table of contents from headings. D25 had the client derive sections because ingestion never wrote them; M4 closes that.

Why level is always 1

The classifier labels a block as a heading but has no rank for it; inventing levels would be a guess, so v1 writes a flat list.

10Page markers and TOC leakage (ING-4, ING-5)

A block whose only text is a page number on its own line, outside the TOC region, is typed noise and dropped, instead of surviving as a body or list block with empty spoken text. The document 17 findings add three fixes: a heading that is a bare page number is noise, a heading fragment ending in a hyphen joins the next line, and the U+FB00..U+FB06 ligatures decompose in stage 1.

Why it is needed

ING-4 excludes page-number blocks from the reading order; M3 listening found them surviving as empty segments, and document 17 showed TOC numbers leaking in as headings.

Why the TOC region is exempt

TOC lines end in page numbers by design; the rule targets numbers standing alone in the body, not the TOC's own layout.

11Number forms by ear (ING-6)

Before any new normalizer rule, a sampler synthesizes twelve sentences of money, years, fractions, slashes, phone numbers, versions, temperatures and ranges with Kokoro. The user listens and marks which readings are wrong; only those get rules, each with a character-map round-trip test.

12Tables and equations as cues (ING-7)

A table block becomes a spoken cue, "Table N, R rows.", then one segment per row with cells joined by commas; rows with no letters are skipped. An equation block becomes a single segment, "Equation." or "Equation N." when it carries a label like (3); its symbols are never spoken.

Why it is needed

ING-7: tables as row-by-row prose with a cue ("Table 2, 3 rows"), equations as a cue, not symbols.

Why rows without letters are skipped

Separator rows and pure-number padding carry no meaning by ear; reading "dash dash dash" is worse than silence.

13OCR fallback per page (ING-2, D28 proposed)

Stage 1 counts the non-space glyphs on each page. A page with fewer than 20 is rendered at 100 dpi in grayscale; if more than 0.5 % of its pixels are darker than 128, there is ink without text, and the page goes to OCRBackend.recognize. With no engine installed, the page stays empty and the document records how many pages were skipped.

Why it is needed

ING-2: detect per page whether a text layer exists and OCR only the pages without one. Scanned pages are otherwise silent.

Why a subprocess (D28, proposed)

Tesseract is Apache-2.0 and runs as a binary behind OCRBackend, so no OCR engine becomes a Python dependency. It is not installed on the dev machine; the user chooses how to install it, or OCR is tested with the fake backend only in M4 (real test @pytest.mark.ocr, skipped without the binary).

14The 300-page soak gate

A generated 300-page PDF (reportlab, dev-only, a heading every 10 pages, about 20 varied sentences per page) is pushed through the whole system. The API clause checks time, memory, order, audio and cleanup; the browser clause checks render time, sync, navigation and restore; the Docker clause checks the packaged app answers.

Why it is needed

The PRD gate for M4 is "300-page soak passes; Docker up". Every earlier test used short documents; a book-length one is where memory, ordering and rendering cost show up.

Why D29 waits for the numbers (proposed)

If first render passes 5 s or probes fail from scroll jank, the reader renders a window of segments (own code, no new dependency); otherwise M3's "load everything" stays.

15One container serving API and app (D21, D30 proposed)

With D21 the API mounts web/dist at / after its routers, so one process serves both. Compose therefore runs one service, api, built in two stages: a Node stage builds the app, the Python stage installs the API with Kokoro pinned and copies the built app in.

Why it is needed

The gate's second half is "Docker up": a user without Python or Node set up runs one command and gets the app.

Why one service (D30, proposed)

D21 already makes FastAPI the static server; a second web container would only proxy back to it. One service is one port, one log and no CORS.
