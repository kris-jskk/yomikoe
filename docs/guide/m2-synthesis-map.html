HearNarro M2: turning sentences into sound that stays in sync

An architectural guide to Milestone 2. M1 produced an ordered list of sentences. M2 makes each one audible on demand, fast enough that pressing play feels instant, at any speed from half to triple, with word timings that still line up with the text on screen. This page explains the mechanism, why each piece exists, and where the work stands.

The gate that ends M2 First audio within 2 seconds of a play request, at every speed from 0.5x to 3.0x, on a laptop CPU with no GPU. Measured by a benchmark script against the real voice model on a cold cache, and by a contract test against a fake backend in CI. The sentence-boundary metric deferred from M1 is also measured here, and its threshold set once the first numbers are in.

1Why M2 is where the product becomes real

A reader who presses play is willing to wait about as long as it takes a person to clear their throat. Longer than that and the app feels broken. Speech synthesis on a CPU is not instant: an 82-million-parameter model produces a sentence in a few hundred milliseconds to a couple of seconds, depending on length. So M2 is not only "call the model"; it is the machinery that hides the model's latency: synthesize one sentence at a time, start playing the first while the next five are being made, cache everything so a second listen costs nothing, and do all of it on one dedicated thread so the API stays responsive.

The second half of M2 is honesty of timing. The model reports when each word starts and ends. Those timings are what highlight the word being spoken in M3. If they drift, even by half a word, the highlight looks wrong and the reader stops trusting it. Every transformation in this milestone, speed changes above the model's range included, has to carry the timings along exactly.

One sentence per synthesis call

The sentence is the unit of playback, seek, resume and voice change. It is also the size at which the model is both fast and good; quality drops and latency grows past about 300 characters.

A backend interface, not a model

TTSBackend is the only place a model is named (SYN-4). Tests use a fake backend that returns silence with synthetic timings, so CI needs no model download and runs in seconds. Kokoro is the first real implementation; a GPU model later is a drop-in.

Cache by segment id

Audio is keyed by (segment, voice, speed, backend). Re-listening is instant (SYN-6), and because the key is the segment id rather than a text hash, re-ingesting a document never serves stale audio.

Measured, not assumed

The 2-second target is a benchmark number on this machine, written to a file with a date. The PRD lists "is 2 s realistic on an M1 laptop" as an open question; M2 answers it with a measurement in its first week.

2The synthesis flow

One request for one sentence's audio passes through six stages. The first thing checked is the cache; on a hit nothing else runs. On a miss the request jumps ahead of any queued lookahead work, because the listener is waiting on this sentence and not on the ones after it.

3The lookahead queue

The queue is the trick that makes a slow model feel fast. Synthesis takes a fraction of the audio's own duration, so while one sentence plays, the thread has time to make several more. The service keeps a window of five sentences ahead of the one playing. When one finishes, the window slides. Anything already cached is skipped. A play request for a sentence outside the window jumps the queue, and a seek throws the whole window away and rebuilds it from the new position, so scrubbing through a document never piles up stale work.

4Speed: the native range and the stretch region

Kokoro takes a speed value and applies it inside its duration predictor, which is the best way to go faster: the model shortens vowels and pauses the way a fast speaker does, and the timings it reports are already correct. It is clean between 0.5x and 2.0x. Above that, consonants clip. So for 2.1x to 3.0x the service synthesizes at 2.0x, stretches the audio by the remaining ratio (at most 1.5, inside the range where stretching is artifact-free), and divides every timing by that ratio. Both the 2.0x file and the stretched file are cached, keyed by the speed the user asked for.

5Keeping word timings honest

The model reads normalized_text ("3.2 percent"); the reader shows text ("3.2%"). Timings come back against the spoken form, so the API translates each word's character span through the segment's character map before caching. The browser never sees spoken-text offsets. After a stretch, every start and end is divided by the same ratio, so the relative positions do not move. Two invariants are tested on fifty fixture sentences at every speed: timings are sorted and non-overlapping, and the last one ends no later than the audio does.

6Delivery to the browser

Decision D5 replaced the original WebSocket-plus-MSE plan with one HTTP request per sentence. The browser fetches GET /audio/{segment_id}?voice=&speed=, decodes the response with decodeAudioData, and schedules the buffer to start exactly when the previous one ends on the Web Audio clock. That is gapless by construction, and the same clock drives the word highlight in M3. M2 builds the server side of this: the endpoint, the headers, the blocking cache miss, and a HEAD probe so the client can ask "is it ready" without downloading.

7Sentence boundaries, measured

M1's gate measured reading order at word level and deliberately ignored where sentences are cut, because the cuts in the ground truth came from the old extractor. M2 is where cuts become audible: a sentence split in two gets two synthesis calls, two prosodic contours and a pause in the middle; two sentences merged get one long contour. So M2 builds a boundary truth and a metric. The truth is the same ordered words as the reading-order truth with reviewed line breaks, which lets a validator prove nothing but the breaks moved. The metric aligns the parser's word stream to the truth's and scores boundaries as precision and recall.

8Dependencies and licences, settled before code

M1 found its extractor was AGPL after the parser was built, and paid for the swap. M2 does the survey first. Three questions are open on this machine, which has no Homebrew, no ffmpeg and no espeak:

  • Which Kokoro runtime, and how it turns text into phonemes. The common path uses espeak-ng, which is GPL-3. The G2P library Kokoro ships with (misaki) is Apache-2.0 and handles most English without espeak; what it does for words outside its lexicon decides whether the GPL fallback is needed at all. Also: whether the ONNX build exposes per-token timings and a speed input, and the pinned revision of the Apache-2.0 model weights.
  • How to encode Opus without ffmpeg. ffmpeg is LGPL or GPL depending on the build; the project's rule is Apache, MIT or BSD. libopus itself is BSD. The survey lists Python packages that write Opus from wheels on Apple Silicon and whether Safari, including iOS, decodes each container. WAV needs nothing and decodes everywhere; it is the fallback and the test path.
  • How to time-stretch without ffmpeg. A pure-numpy WSOLA or an MIT library replaces atempo if ffmpeg stays out.

The interfaces in the spec are written so that none of these choices changes the service, the cache, the queue or the API: the backend, the encoder and the stretch function are each one module behind a fixed signature.

6. Listening test Why: no automated test hears the audio; the first listener finds what the invariants cannot.
  • Server on port 8765 with Kokoro, a one-line helper to fetch and play any sentence of the user's documents at any speed and voice.
  • Finding: at 1.0x the Almanack sentence sounds right; at 2.0x the first word, or its first letters, is missing. Two candidate causes being measured rather than guessed: the model clipping the first consonant at its top native speed (the design warned of clipping above 2.0; it may begin at 2.0), or the backend trimming leading audio in a way that fails at higher speeds. The worker compares onset energy and first-word timing at 1.0, 1.5 and 2.0 across five sentences, checks the upstream pipeline as a reference, then fixes at the right layer with a model test that would have caught it.
  • Root cause, measured: the model. Kokoro divides every predicted duration by the speed, including the leading start token, and renders its first 250 to 330 ms as near-silence whatever is scheduled there. At 2.0x the start token shrinks from 325 to 175 ms, so the first word lands inside the silent start: 35 dB below its 1.0x level, and 10 dB down already at 1.5x. The upstream pipeline shows the same onset, so nothing in our code caused it. Lowering the native ceiling or adding a leading pause did not help.
  • Fix: the backend floors the start token's duration at its 1.0x value before synthesis, in its own inference wrapper around the vendored model. After the fix the first word is within 3.6 dB of its 1.0x level at 1.5x, 2.0x and 2.5x across all five sentences; audio at 1.0x and below is bit-identical to before. A model test now checks the first word's level against 1.0x at three speeds; it failed on the old code and passes on the fix. The earlier guess that the player was at fault is logged as a correction in the supervisor log.
  • Speed steps (user request, commit 3e4bf2d): the API now accepts 0.5x to 3.0x in 0.05 steps, so 1.25x and 1.75x work; cache names carry two decimals; SYN-3 in the PRD updated. 497 tests pass.
  • Acronyms (user finding, done, commit 8d04c63): "TED" was read as T E D because the M1 normalizer spelled every all-caps token not on a short allowlist. The decision moves to the backend, which has a pronunciation lexicon, in this order: override lists, known collocations ("TED talk"), the document's own definitions recorded at ingestion ("Transferable Erosion Deposit (TED)" means an initialism), the lexicon, then a pronounceability heuristic; every decision logged per document for later per-document overrides. Ingestion gains a definition scanner and the document row a column for them (migration 0003). Measured on 18 tokens before and after: TED, NASA, NIST, OPEC, FIFA, NATO, IKEA spoken; CEO, PDF, HTML, USB, FBI, AI, UK, IBM, SQL, GPU spelled; JSON spoken as "Jason" by an explicit respelling. In the user's O'Reilly report the scanner found "BLE (Bluetooth Low Energy)", so BLE is spelled there. The user's four documents were re-ingested so their stored spoken text no longer carries the old spelled-out forms.
  • Names the lexicon does not know (user finding, done, same commit): "Uber" came out as "yuber" because the fallback guesses from spelling. The user rejected a hand-maintained override list as unsustainable, rightly. The approach became: a second lexicon tier from the CMU Pronouncing Dictionary (about 134,000 entries, permissive licence, mapped onto Kokoro's phoneme set) between Kokoro's own lexicon and the fallback; the fallback's quality measured on 200 names and terms (coverage per tier, phoneme error rate against the dictionary) so a stronger guesser is chosen by numbers if needed; an override file kept only as an escape hatch; and, in M4, corrections made by the listener in the reader, remembered per document or globally, as the sustainable form of a custom list. Measured on 200 names and terms: Kokoro's lexicon knew 107, the dictionary tier added 53, 40 still reach the fallback, whose phoneme error rate against the dictionary is 9.5 %. The PyPI dictionary package is GPL, so the BSD-licensed dictionary file itself is vendored at a pinned commit. "Uber" is in neither lexicon with its common reading, so it is the override file's one entry.
  • Pause after every sentence (user finding, done, commit 8f20b41): two sources being measured apart. The listening helper fetched each clip only after the previous one ended and then started a new player process, which the M3 player never does; it now prefetches. Inside each clip the model adds trailing silence and, since the first-word fix, a little leading silence at higher speeds; a trim step in the synthesis path cuts both to a fixed short pad (60 ms in, 150 ms out, configurable) and shifts the timestamps, so the gap between sentences becomes short and constant in the product too. Measured on ten sentences: the model left 315 ms of silence before and 470 ms after each clip at 1.0x; after the trim, 60 and 150. Three consecutive Foreword sentences joined end to end: gaps 870 ms before, 210 ms after. The helper's player start-up (about 0.8 s per clip) was the other half of what the user heard; the helper now joins the fetched clips into one file and plays it once, which is what the M3 player does on the audio clock.
  • Domain names (user finding, done, commit d468b70): "shopping.com" and "vast.com" lost their dot, because the normalizer reduced addresses to a bare domain and the voice treated the dot as punctuation. The normalization rule becomes: a domain-shaped token is spoken as "name dot tld", "www." dropped, short paths read with "slash", emails as "name at host dot tld"; every spoken character still maps onto its source so highlighting stays exact; the splitter must not cut at the domain's dot. Result on the user's documents: "Vast dot com and Epinions … Shopping dot com", "Navalmanack dot com", "corporate at oreilly dot com", "Twitter dot com slash Naval"; a line-broken "www. ericpartaker.com" is one sentence again. Only lowercase TLDs count as bare domains, so a missing space after a full stop is not read as an address. 603 tests pass; documents re-ingested.
  • Page navigation (user request): the helpers accept p13 for "start at PDF page 13"; the API version (a page parameter on the segments endpoint and a table of contents from headings) is queued behind the acronym change, which touches the same files.
