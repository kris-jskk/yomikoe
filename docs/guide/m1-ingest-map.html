HearNarro M1: turning a PDF into readable sentences

An architectural guide to Milestone 1. It explains what the ingestion pipeline does, why it is built test-first against a fixture set, what each step in the current work sequence is for, and where things stand.

The gate that ends M1 20 fixture PDFs, each with a hand-checked expected reading order. The parser must score at least 0.95 on every PDF and 0.97 on average (thresholds from the PRD, unchanged). 1Why M1 is the risky milestone

HearNarro reads a PDF aloud with word-level highlighting. Every later feature (synthesis, seeking, resume, skip-a-footnote) operates on one thing: an ordered list of sentences, each pinned to where it came from on the page. If that list is wrong, the listener hears a column interleaved with its neighbor, a page number read out mid-sentence, or a footnote in the middle of a paragraph. No amount of voice quality repairs that.

A PDF does not store reading order. It stores glyphs at coordinates. Two-column papers, running headers, rotated margin stamps, tables and equations all look alike to the file format. The PRD names reading order on real-world PDFs as the top risk to v1, and its mitigation is the one this guide describes: build the measuring stick first, then the parser.

2Why fixture PDFs with ground truth

The parser is a stack of heuristics: font-size ratios, column-gap thresholds, band widths. None can be proven right; each can only be measured. The fixture set is the measurement. Twenty real PDFs, each with a file that says what a careful reader would read and in what order, turn "the parser looks fine" into a number per PDF that every later change is held to.

Four classes, four failure modes

Two-column academic papers test column detection. Single-column NIST reports test header, footer and cover-page handling. Table-and-equation-heavy papers test block typing. Scanned pages (image only) test the OCR fallback, which lands in M4.

Real documents, not synthetic ones

Synthetic pages only contain the problems the author thought of. Real arXiv and NIST PDFs bring the rotated arXiv stamp, small-caps running headers, equation subscripts as separate text blocks. The baseline below found all three.

Redistributable, small, repeatable

Every fixture is CC-BY-4.0 or US public domain, with source and license evidence recorded next to it. Each is trimmed to 4 pages so the set is 9.8 MB and the gate runs in seconds. Four pages keeps the header-repetition rule testable.

Hand-corrected, then frozen

The parser's own output is the draft; a reviewer checks it line by line against page images and fixes order, drops noise, joins split sentences. Freezing matters: if the expected file were edited to match the parser, the test would measure nothing.

3The ingestion flow

Ingestion is a pure function from a PDF to a list of segments, run once per upload. Each stage is its own module with its own unit tests, so a bad reading order can be blamed on one stage. The data narrows at each step: from positioned glyph runs, to typed blocks, to an ordered list, to merged text, to sentences.

stage 1ExtractING-2 · D1

What: pdfplumber (MIT, on pdfminer.six) yields every character with its bounding box, font name, size and orientation. The stage groups characters into spans, lines and blocks itself, in content-stream order, keeping bold, italic and superscript flags from the font names and sizes. A page whose text layer yields fewer than 20 characters is rendered at 300 dpi with pypdfium2 and sent to Tesseract, which produces the same span structure. PyMuPDF was the original choice; it was replaced on 2026-10-16 (D13) because its AGPL licence conflicts with the project's dependency rule.

  • Why spans and not plain text: font size drives heading detection, the bounding box drives everything else. Flattening to text here would throw away the only signals the later stages have.
  • Why keep line direction: rotated margin stamps (the arXiv id down the left edge, the NIST "available free of charge" stamp) are real text in the file. Their only distinguishing feature is a vertical text direction. This field was added after the ground-truth review found both.
  • Why OCR is optional here: Tesseract is a system binary. The stage reports "no text layer" and continues when it is missing, so the rest of the gate still runs.
stage 2ClassifyING-3

What: each block gets one type from a rule table, first match wins. The body font size is the character-weighted median across the whole document, not per page, so a page of headings cannot fool it.

stage 3OrderING-4 · D2, D3

What: per page, keep the readable types, drop header, footer and noise, defer footnotes to the end of the page, detect one or two columns from the horizontal positions of the blocks, and emit column 1 top to bottom, then column 2, then the footnotes. Section 4 draws it.

  • Why geometric and not a layout model: every ML layout model with good two-column accuracy either pulls in PyTorch and GPL code (Marker) or needs a GPU. Geometry clears two-column papers and single-column reports, which is v1's scope; magazines and sidebars fail visibly against the fixtures rather than silently.
  • Why footnotes go last: a listener wants the paragraph, then the note, not the note interrupting the sentence it annotates.
stage 4MergeING-5

What: join the lines inside a block with a space; when a line ends in a hyphen and the next starts lowercase, drop the hyphen and join directly. When a body block ends without terminal punctuation and the next body block in reading order starts lowercase, join them into one logical block.

  • Why join across breaks: a sentence that starts at the bottom of column 1 and ends at the top of column 2, or on the next page, must be one segment. The TTS synthesizes per segment; a sentence cut in two gets two prosodic contours and an audible seam. The design wrote this rule for page breaks; the ground-truth review showed column breaks need it just as much.
  • Why keep source references: each logical block records the (page, index) of every raw block it absorbed, so a segment can always be traced back to its place on the page for highlighting and debugging.
stage 5SegmentING-5, ING-6 · D4

What: pysbd splits each logical block into sentences with clean=False, so every sentence keeps exact character offsets into the block's text. A normalizer then writes the speech-friendly form next to it and records, for every output character, which input character it came from. Section 5 draws that mapping.

  • Why sentences: Kokoro's quality drops and latency grows past about 300 characters; a sentence is the natural seek and resume unit; a mid-playback voice change is simplest when the unit of synthesis is the unit of playback.
  • Why a rule-based splitter: pysbd handles abbreviations and citations better than a regex and has no model to download. Its remaining mistakes ("Eq." and "Natl." treated as sentence ends) are known and recorded; the ground truth deliberately keeps its boundaries so the gate measures order, not the splitter.

4Reading order up close

Stage 3 is where two-column papers are won or lost. The mechanism is small enough to draw in full. For each page: project every block's horizontal midpoint onto the x axis; if the midpoints form two clusters separated by a gap wider than 8% of the page width, the page has two columns and the gap's center is the split. A block wider than 60% of the page is full-width and acts as a column break: everything above it in both columns is read first, then the block, then both columns below it.

Prior art: is this already solved?

Checked on 2026-10-16 (survey with sources in _agent/results/90_prior_art_survey.md). Tools that solve two-column reading order well are ML layout models: Marker and Surya (code Apache-2.0, but weights restricted above $5M revenue), MinerU (Apache-2.0 plus revenue and attribution conditions), DocLayout-YOLO (AGPL), Nougat (weights non-commercial). Permissive end to end, with reading order: PaddleOCR's PP-DocLayoutV3 (Apache-2.0 code and weights, predicts reading order in the detector, CPU-capable) and Docling's layout path (MIT code, Apache-2.0 layout model; its table model carries a permissive but differently named licence). Permissive text extractors with no layout model: pdfplumber and pdfminer.six (MIT), pypdfium2 and pdftext (Apache-2.0). Published reading-order benchmarks exist only for the ML tools; none for the plain extractors' sort modes, whose docs do not claim column handling.

The finding that matters most: PyMuPDF, the extractor the PRD chose, is licensed AGPL-3.0 or Artifex commercial. That does not satisfy the project's rule that every shipped dependency is Apache-2.0, MIT or BSD. Stage 1 has to move to a permissive extractor (pdfplumber for spans, fonts, drawings and tables; pypdfium2 for rendering) whatever happens with stage 3. Decision pending with the user.

What the baseline showed this mechanism getting wrong, and what tuning targets: floats that sit in one column but cross the split by a little are assigned by midpoint and interleave both columns; cells of a detected table come out as separate blocks and scatter; and because the merge rule only joined across page breaks, every column break left a sentence in two pieces.

5The segment model: three coordinate systems pinned together

A segment carries the text the reader sees, the text the TTS speaks, and a map between them. The TTS returns word timestamps against the spoken text; the reader highlights the displayed text. Without the map, "3.2 percent" (11 characters) highlighting "3.2%" (4 characters) drifts by 7 characters, and the error compounds across the sentence.

This is why stage 5 is in M1 even though full speech normalization (ING-6) is an M4 item: the map's invariants (same length as the spoken text, every index inside the displayed text, non-decreasing) are unit-tested now, so M2's timestamp tests can rely on them.

5bThe skeleton: where segments land

The pipeline is a pure function; the skeleton is what makes its output reachable. An upload is hashed, stored once, recorded as a document, and parsed off the request thread in a process pool, because pdfminer holds the GIL for long stretches and a 300-page parse must not stall the API (D9). Blocks and segments are written in one transaction and the status flips to ready only then, so a reader never sees a half-written document. The schema is the Technical Design's DDL, applied by an Alembic migration from day one (D7).

How the session is run

The interactive session supervises: it gathers state, splits the work, writes briefs, reviews what comes back and makes the judgment calls. Fresh worker agents do the building, each with a self-contained brief, a numbered list of claims it must settle, a tool-call budget, and an explicit set of files it may touch. Every "it passes" in a report points at a saved command output under _agent/results/, and two of those are opened per report before the report is trusted. Root-cause attribution stays with the supervisor, which is why the two causes in phase 4 were checked directly against the PDFs rather than taken from a reviewer's reading. Nothing is pushed; every commit is local on the branch.
